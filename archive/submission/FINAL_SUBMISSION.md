# GemmaForge

**Subtitle:** Local, repo-wide vulnerability auditing with two Gemma 4 models — a small one finds candidate bugs, a larger one reads them and decides.

## What we built

GemmaForge is a tool for finding security vulnerabilities in source code without sending the code anywhere, either in existing repos or freshly AI-generated code. It runs two Gemma 4 variants locally on the repo including a white-box probe on model activations. The smaller one scans the repository and flags code that looks like the kind of thing that gets CVEs filed against it. The larger one picks up those flags as a worklist and acts as a tool-using auditor: it reads the files, greps the call sites, and produces structured verdicts. Both models share a tokenizer, a license, and a single JSONL schema, so the pipeline is one consistent stack from triage to verdict, with no network call anywhere in the loop.

The scanner is the part we built from scratch. We trained a single-layer linear classifier on a hidden state of Gemma 4 E2B (around 2B parameters, layer 17 of 35). The training label is binary: does this snippet match the vulnerable side of a known patch pair, or the patched side? The classifier itself is about 1,500 params and adds negligible overhead on top of Gemma's forward pass. To audit a repository we walk the files with a sliding line window, run each chunk through Gemma 4 to capture the activation at layer 17, and aggregate the per-position scores with a top-k mean. Each chunk that crosses a confidence threshold becomes a "lead" — file, line range, snippet, confidence, and a predicted CWE class from a separate five-head one-vs-rest classifier that covers CWE-78, 94, 95, 328, and 338. Leads are written out as a `gemmaforge.leads/v1` JSONL stream that anything downstream can consume.

The auditor is Gemma 4 31B running locally through Ollama with the pwnkit agentic stack, an agentic pentest framework maintained by Doruk. We added two pull requests to pwnkit (#371 and #372, roughly 3,000 lines, both merged) that teach it to read our lead schema, prepend the leads to its internal worklist, drive Gemma 4 via Ollama's native function-calling API with streaming tool-calls, and stream the resulting verdicts back into a live dashboard. The dashboard has three lanes: every per-chunk probe firing, the leads that survived the threshold, and the agent's verdicts on each lead. Clicking a verdict highlights the originating probe lead by file and line.


## Why this is useful

AI coding assistants now write a significant share of the code that reaches production, and a measurable fraction of that code is insecure in fairly predictable ways: string-interpolated SQL, unvalidated paths, command-injection sinks, weak crypto, hardcoded secrets. The standard answer is to scan it afterwards with Snyk, Semgrep, or CodeQL. That answer has three problems for the people who need it most. It runs too late, after the developer has already pasted the suggestion. It requires uploading the code somewhere, which excludes solo maintainers, air-gapped enterprises, regulated industries, and a long tail of people for whom a Snyk seat costs more than a month of rent. And the rules it runs are static: they only catch what someone wrote a pattern for, and they never tell you that the model itself was uncertain about what it wrote.

The premise of this project is that the model that produced the code already has a usable signal about which of its outputs look risky, and that we can read that signal cheaply by training a tiny linear head on its hidden states. The premise of the second tier is that the same model family, scaled up, can take those cheap signals and turn them into verified findings by actually reading the files like a junior auditor would. Both tiers run locally on the same machine.

## How it performs

The headline evaluation is a cross-language split: we train the probe on Python and test it on JavaScript, on a position-paired CyberSecEval corpus of 1,198 patch pairs. AUC on that split is 0.907 at 81.9% accuracy. In-distribution AUC with random stratified splitting is 0.960, and with a group-by-repo split that controls for repository-level leakage it is 0.958. Holding out individual CWE classes one at a time gives 0.92 to 0.96 depending on which class is held out. The five-head per-CWE classifier reaches a macro AUC of 0.973.

We also evaluated the repo-scanning shape of the product on 136 held-out SVEN micro-repositories built from a deterministic 80/20 group split, so the probe never saw those vulnerable files during training. On that benchmark, a clean span-max probe trained only on the SVEN train split ranks the true vulnerable location in the top 5 leads for 59.6% of repos and in the top 10 for 67.6%, with 20.6% precision@1 and MRR 0.364. That is the right operating point for GemmaForge: Tier 1 is not trying to prove exploitability by itself, it is trying to give the larger auditor a short, high-signal worklist instead of an entire repository.

We were challenged early on about whether the cross-language number was really measuring snippet length rather than vulnerability content, because a length-only baseline reaches AUC 0.883 on the same unmatched eval. We rebuilt the eval with length-matched pairs (230 pairs balanced within roughly three characters per class). On that controlled eval the length baseline collapses to 0.514, essentially chance, while the probe still scores 0.843. So the original 0.907 was not mostly length. There is one class where a regex baseline beats the probe outright — CWE-328, weak-crypto API names — which is a fair win for static patterns.

We also stress-tested the probe with the standard surface-form adversarial suite from the recent literature (Bailey et al. 2026, RL-Obfuscation 2025). Identifier renames and SQL case shifts move the probe's output by less than 0.01 AUC, which rules out the simplest "you're just detecting API names" reading. The one transformation that hurts is reindenting and adding comments (Δ −0.087 on last-token scoring). Switching the serving-time aggregation from last-token to an 8-token max-pool reduces that drop to roughly 0.005 at a cost of 0.031 clean AUC.

## Why Gemma 4 specifically

Three things have to hold for this design to work, and only Gemma 4 gives us all three. The probe needs raw hidden states at every layer, which closed models like GPT-5 and Claude do not expose. The auditor needs native function-calling and a context window large enough to fit a small repository in one shot, which Gemma 4 31B provides with its 131k window and `tools[]` schema. We need small and very strong models like the Gemma's E2B/E4B variants. Llama or Qwen would give us hidden states, but their small variants are too slow to run across whole codebases. Gemma 4 is the only family where the same architecture spans the laptop-class probe backbone and the workstation-class verifier.

## What is shipped

Everything described above is in the repository and in the two merged pwnkit PRs. The probe weights, dataset generation code, evaluation code, the scanner, the lead schema, the dashboard wiring, and the evaluation receipts are all in this repo under Apache-2.0. The Gemma 4 weights are used under the Gemma Terms of Use, which allows commercial use. The training data was derived only from publicly disclosed CVE patches and datasets. The end-to-end demo is `python -m src.scan ./repo > leads.jsonl` followed by `pwnkit review ./repo --seed-findings leads.jsonl --seed-only --runtime ollama`. Both commands run fully locally.
