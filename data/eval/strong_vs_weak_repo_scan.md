# Repo-level scan benchmark — `strong-probe` vs `weak-probe`

End-to-end scan over the 687 micro-repos in `data/repo_benchmark/`
(generated by `scripts/build_repo_benchmark.py` from `data/dataset.jsonl`,
schema `gemmaforge.repo_benchmark/v1`).

Each repo has a vulnerable file, a fixed counterpart, and several safe
decoys. The scanner emits ranked leads; a lead "hits" a manifest trace
if it overlaps the trace's char range in the right file. Reports:
`data/eval/repo_scan_report_weak.json`, `data/eval/repo_scan_report_strong.json`.

## Configuration

|                  | weak-probe                 | strong-probe                |
|---               |---                         |---                          |
| Backbone         | `google/gemma-4-E2B-it`    | `google/gemma-4-E4B-it`     |
| Probe            | `data/probe.npz` (L17)     | `data/probe_strong.npz` (L10) |
| Scan profile     | `weak-probe`               | `strong-probe`               |
| Line window      | 30                         | 120                          |
| Line stride      | 20                         | 80                           |
| Token window     | 512                        | 2048                         |
| Token stride     | 256                        | 1024                         |
| Wall time        | 890 s                      | 1056 s                       |
| s/repo (3090)    | 1.3                        | 1.5                          |
| Per-CWE head     | enabled (`probe_per_cwe.npz`) | bypassed (layer mismatch) |

## Reading

**Strong probe is the right pick for any K ≥ 5.** For K=10 it finds the
vulnerability in 85 % of repos vs the weak probe's 73 %; for K=25 it's
97 % vs 88 %. Precision rises too — strong's top-25 leads contain 17 %
true hits vs weak's 12 %, so the larger windows aren't just bigger
haystacks, they're better-aimed.

**Strong probe loses at K=1.** repo_recall@1 drops from 5.5 % to 1.0 %.
This is the chunking, not the probe quality:

- The strong scan uses 120-line windows vs 30-line. A 120-line window
  picks up the vulnerable region *plus* a lot of surrounding context.
  Per-chunk confidence is dominated by whatever the probe thinks is the
  strongest signal in that window — frequently a lookalike pattern
  elsewhere in the file.
- MRR is almost identical (0.240 vs 0.237), so the *first true hit*
  lands at roughly the same average rank either way. The strong probe
  is mostly relocating that hit a few ranks deeper, not failing
  outright. By rank 5 it's already pulled ahead.

**Operational implication.** A reviewer who only looks at the top
finding will be worse off with strong-probe (1 % vs 5.5 %). A reviewer
who looks at top-10 will see ~12 percentage points more true hits with
strong-probe. The product's actual UI shows top-K leads in the Hunt
lane (#371 of pwnkit), so K=10–25 is the relevant operating point and
strong-probe wins.

**The per-CWE head is broken on strong-probe.** The shipped
`data/probe_per_cwe.npz` was trained at layer 17 (E2B). The strong
probe is at layer 10 (E4B). The adapter asserts they match and
refuses to load. The strong scan in this report was run with
`--per-cwe-probe-path /tmp/_nonexistent.npz` to bypass the assertion;
the CWE routing column in the JSON is therefore absent for strong
(weak shows 0.0 across the board because the per-CWE head trained on
the old layer-17 acts has its own issue, separate from this work —
worth a follow-up).

## What's *not* tested here

- Multi-vulnerability repos. Every micro-repo has exactly one positive
  region; trace_recall and repo_recall are degenerate in the same way.
- Real-world repo noise. Decoys are unrelated safe snippets, not
  same-codebase distractors. A "real" eval needs CWEval / SecureAgentBench-
  style outcomes; the schema doc (`docs/repo-benchmark-schema.md`)
  flags this explicitly.
- Length confound (#22). The strong probe's larger windows might be
  recovering more of the length-correlated signal that #22 documented
  for the sample-level path. Worth a length-matched repo subset.

## Reproduce

```bash
# weak
python scripts/run_repo_scan_benchmark.py \
  --probe-profile weak-probe \
  --probe-path data/probe.npz \
  --model-id google/gemma-4-E2B-it \
  --leads-dir data/repo_benchmark/leads_weak \
  --out-json data/eval/repo_scan_report_weak.json

# strong (per-CWE head bypassed via fake path)
python scripts/run_repo_scan_benchmark.py \
  --probe-profile strong-probe \
  --probe-path data/probe_strong.npz \
  --per-cwe-probe-path /tmp/_skip_per_cwe.npz \
  --model-id google/gemma-4-E4B-it \
  --leads-dir data/repo_benchmark/leads_strong \
  --out-json data/eval/repo_scan_report_strong.json
```

`leads_weak/` and `leads_strong/` (≈14 MB each) are gitignored; the
two `.json` reports are the canonical artifacts.
